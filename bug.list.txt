[OPEN] BUG-001: Root URL serves leaked MID content via RefererTracker state

  Summary:
    After visiting /memns/{name} or /mem/{mid}, the root URL (/) on BOTH
    localhost and public gateway starts serving that MID's content instead
    of its normal behavior (domain resolution on public, 404 on local).

  Reproduction:
    1. Start local node on localhost:8081
    2. Add a memns name record via explorer (e.g. /memns/kss...)
    3. Visit localhost:8081/memns/kss... — content renders correctly
    4. Visit localhost:8081/ (root) — now shows the SAME content
    5. Public gateway (gateway.membuss.dpdns.org/) also shows it
    6. When nothing is published, root correctly shows "memlink not found"

  Root Cause:
    RefererTracker in memgate_v2 has TWO problems:

    A) Global shared state: `recentMIDs` is a server-wide MRU list, NOT
       per-client. ANY client visiting /memns/kss adds that MID to the
       global list. All other clients then see it leaked at root.

    B) Cookie fallback: `setMIDCookie()` sets a 1-day cookie on ANY
       MID access (/mem/, /memns/, subdomain). The cookie fallback in
       Resolve() probes MemFSPathInfo(root, "") which succeeds for any
       directory-type MID, causing unrelated content at root.

    The execution order in Handler() (line 246-251) is:
      1. isSystemPath("/") returns false
      2. Not a subdomain, not /mem/ or /memns/
      3. RefererTracker.Resolve() runs BEFORE the chi router
      4. Fallback 1 (recentMIDs) or Fallback 2 (cookie) matches
      5. serveMemFSPath() serves content — customDomainMiddleware never runs

  Affected Code:
    - gateway/memgate_v2/memgate.go:246-251 (Handler runs referer before router)
    - gateway/memgate_v2/memgate.go:271-286 (isSystemPath: "/" returns false)
    - gateway/memgate_v2/memgate.go:258-268 (setMIDCookie: 1-day cookie)
    - gateway/memgate_v2/referer_tracker.go:21-26 (global recentMIDs)
    - gateway/memgate_v2/referer_tracker.go:183-195 (Fallback 1: recentMIDs)
    - gateway/memgate_v2/referer_tracker.go:197-209 (Fallback 2: cookie)

  Fix Options (pick one):

    Option A (simplest): Skip referer resolution for root path
      - In Handler(), add: if path == "/" { skip referer resolution }
      - Pros: minimal change, no behavior regression for asset resolution
      - Cons: root never resolves via referer (but it shouldn't)

    Option B: Scope recentMIDs per client IP
      - Change recentMIDs from []string to map[string][]string keyed by IP
      - Pros: fixes the global leak
      - Cons: more complex, doesn't fix the cookie issue

    Option C: Remove cookie-based fallback entirely
      - Delete the cookie fallback in Resolve() and setMIDCookie()
      - Pros: removes persistent state that survives restarts
      - Cons: may break legitimate relative asset resolution

    Recommended: Option A + remove cookie fallback (combine A and C)

  Testing Steps:
    [ ] Start local node, add memns name record
    [ ] Visit /memns/{name} — content renders
    [ ] Visit / — should NOT show that content
    [ ] Visit / on public gateway — should show domain resolution
    [ ] Clear cookies, restart daemon, visit / — no leaked content
    [ ] Relative assets (CSS/JS in /mem/{mid}/site/) still resolve
    [ ] Subdomain routing still works

  Scope: gateway/memgate_v2 (v1 deprecated, same pattern exists)
  Severity: Medium — confuses users, shows wrong content at root
